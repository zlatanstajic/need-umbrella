# Repository Instructions

These instructions apply to every agent working in this repository.

## Before editing

- Read a file before changing it.
- Search all callers before changing a function or shared type. Use `rg` or
  `rg --files` for discovery.
- Read [`CLAUDE.md`](CLAUDE.md) for detailed architecture and behavior before
  making non-trivial application changes.
- Preserve existing user changes and keep unrelated work out of the patch.

## Source ownership

- [`src/`](src/) is the source of truth for application logic. The entry point
  is [`src/app.ts`](src/app.ts), and domain types belong in
  [`src/types.ts`](src/types.ts).
- [`index.html`](index.html) owns markup, metadata, and static DOM structure.
- [`assets/css/style.css`](assets/css/style.css) owns styling.
- [`tests/`](tests/) contains Vitest tests as `*.test.ts` files.
- [`assets/js/app.js`](assets/js/app.js) is generated and committed. Never edit
  it by hand; regenerate it with `npm run build` after TypeScript changes.
- [`assets/img/og-image.png`](assets/img/og-image.png) is generated by
  [`scripts/gen-og-image.py`](scripts/gen-og-image.py). Change the generator,
  then regenerate the PNG rather than editing the image directly.

## Coding conventions

- Keep TypeScript strict and reuse existing domain types.
- Inside module bodies, match the established pre-ES6 style: use `var`,
  function declarations, and string concatenation; avoid `let`, `const`, arrow
  functions, and template literals. Module-level imports, exports, and type
  annotations are expected.
- Put every user-facing string in both language bundles in
  [`src/strings.ts`](src/strings.ts): Serbian Latin (`sr`) and English (`en`).
- Build UI with DOM methods instead of `innerHTML`.
- Reuse CSS custom properties from `:root` rather than hard-coding colors.
- Route persisted state through the central `store.get` / `store.set` API and
  keep the single `nu:data` storage schema backward-compatible.
- Preserve slot-aware behavior for primary and comparison weather cards.
- Guard asynchronous weather and geocoding results against stale requests.
- Do not add a dependency, framework, backend, or build-system change without
  explicit approval.

## Testing and verification

Run checks in proportion to the change. Before handing off a production code
change, run:

```bash
npm run typecheck
npm test
npm run build
```

Run `npm run test:coverage` for broad logic changes or before release; the
global line-coverage gate is 90%. Tests use Vitest with jsdom and import the
TypeScript source, never the generated bundle.

For UI changes, also verify the affected behavior in a browser when practical:

- Serbian and English text
- narrow/mobile and desktop layouts
- primary and compare modes where applicable
- persistence across reloads
- browser console errors

Use fake timers and explicit system times for time-dependent tests. Keep test
fixtures timezone-independent.

## Documentation and generated output

- Keep [`README.md`](README.md), [`CONTRIBUTING.md`](CONTRIBUTING.md), and
  [`CLAUDE.md`](CLAUDE.md) synchronized with behavior and workflow changes.
- After TypeScript changes, include the rebuilt `assets/js/app.js` in the
  working tree.
- Keep social metadata URLs rooted at
  `https://zlatanstajic.github.io/need-umbrella/`, including the
  `/need-umbrella/` path segment.
- Keep the document head English-only; runtime application copy remains
  bilingual.

## Git discipline

- Do not run `git add` unless the user explicitly asks.
- Never stage or commit changes on your own initiative.
- Do not discard, reset, or overwrite unrelated working-tree changes.
- If branch creation is requested, branch from `master` and use
  `issues/<issue-number>-<short-description>` (lowercase kebab-case).

## Secrets

- Never read or write `.env` files.
- Never expose secrets in code, logs, tests, or chat output.
- Use environment variables for sensitive values and ask the user for access
  when a task requires a secret.
